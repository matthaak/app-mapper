# MD Editor

The Markdown editor (`src/modules/md-editor/`): one document shown two ways, **Visual** (rendered and editable in place) and **Raw** (the source), with tracked changes and comments. Demo at `/md-editor.html`.

## How it works

* **The markdown is the single source of truth.** Every toolbar command is a transform of the markdown, so it does the same thing in either view, and undo works across both.
* **Switching views** carries the selection across exactly — Raw to Visual through the renderer's source map, Visual to Raw through sentinels in the serializer — and keeps the same text at the same height on screen.
* **Tracked changes**: additions `++…++` (underlined) and deletions `~~…~~` (struck through), which Accept and Reject resolve. As in Word, each author's changes are in that author's colour, additions and deletions alike, in both views (the Raw text too). Authors take the colours (`--md-author-1` to `-8`: red, blue, green, violet, teal, orange, magenta, grey) in the order they first made changes, so a colour stays with its author. With Track Changes on, typing becomes the user's additions and deleting their deletions, spaces included: typing on extends the addition at the caret, deleting from it really deletes, and deletions that touch merge into one. Accept and Reject apply to the changes the selection touches, or that the caret is in or right beside. A change with comments keeps its history: Accept or Reject adds the user's "Accepted" or "Rejected" to its thread (nothing, if it already ends that way; the other one flips it). A thread whose last comment is "Accepted" or "Rejected" (any case) marks the change resolved: Visual shows its outcome — the text that stays as plain text, the text that goes not at all (closing up the space it leaves) — and its review box says so; Raw shows the markup as ever. A change with no comments is settled for good: its markup and attribution go, and so does the text it takes out. With Track Changes off, text typed at the very start or end of an addition or deletion goes just outside it (in Visual a caret there can't be told from one just inside, so the editor places it); typed further in, it edits the change's text. Return at the end of a change starts the new paragraph clear of it (the browser would carry the change, attribution and all, into it).
* **List items** can run onto more lines: an indented line under an item (not an item itself) continues it, as a line break — the same as a single newline in a paragraph. Shift-Return in a Visual list item writes one.
* **Tables** (GitHub style): a header row, a delimiter row (`| --- | :---: | ---: |`, setting each column's alignment), then body rows; outer pipes are optional and `\|` is a pipe inside a cell. In Visual, cells are edited in place: a cell holds one line, so Enter does nothing there and typed pipes are escaped. A table written back from Visual uses the plain `| a | b |` form.
* **Highlights and comments**: `^^…^^` highlights, and attribution threads (`@@author.time comment@@reply@@`) on any change, shown, as in Word's review mode, in grey boxes in a review column down the right of the document (a quarter of the editor's width), in both views and at all times. It shows, the length of the document, whenever Review Mode is on, with or without boxes. Each box is tied to its text by a dotted line along the bottom of the text's last line, and centered on that line, so it runs straight into the middle of the box's side; boxes that would crowd each other stack as a cluster centered between its top and bottom lines (moved by up to 10px if that lets one of its lines run straight in), and their lines turn 15px short of the column to reach them — nested where they would overlap, never crossing: of two such lines, the one that can turn inside the other without crossing it does (when either could, the shorter), so the box furthest from its text turns furthest out. Pointing at a box, or at its text in Visual, darkens its line. Click a box to comment or reply in it (Return sends, Escape closes). **Review Mode**, a switch at the right of the Visual / Raw tabs, shows or hides all of this. Off, Visual shows the text as if every open change were accepted (resolved ones as resolved) — no underlines, strike-throughs, colours or highlights — Raw shows the markup uncoloured, the review column is hidden, Track Changes goes off, and Accept, Reject and Accept All are disabled. It starts on for a document with any change or highlight (`annotations` overrides that); highlighting, or using the Track Changes button, always turns it back on. **Accept All Changes** (⌥⇧⌘↩, the double check mark) accepts every change not yet resolved either way, as Accept does one. `onAnnotationsChange(on, manual)` reports it — the mapper remembers a file's setting once the user has set it by hand.

## Files

* `editor.ts` — `MarkdownEditor`: the views, selection mapping, history and input.
* `parse.ts` and `serialize.ts` — Markdown to HTML with a source map, and the Visual DOM back to Markdown.
* `actions.ts`, `track.ts` and `notes.ts` — formatting commands, tracked editing and attribution threads.
* `review.ts` — the review column: its boxes, clusters and lines. `toolbar.ts` — the toolbar's tools and shortcuts. `hasRevisions(md)` says whether a text has additions, deletions or comments (the mapper turns Track Changes on for those). Given `onSave`, the editor shows a Save button (⌘S) at the left of its toolbar, enabled while `modified` is true; `flush()` reports an edit still waiting to be read back. `detachToolbar()` hands the toolbar to the host to show elsewhere; it still acts on its own editor.

## API

`new MarkdownEditor({ value, user, trackChanges, onChange })` mounts anywhere that gives it a size. `value` gets and sets the markdown (setting it clears undo); `onChange` reports edits (Visual edits after a short pause); `mode`, `trackChanges`, `exec`, `undo` and `redo` drive it from outside.
